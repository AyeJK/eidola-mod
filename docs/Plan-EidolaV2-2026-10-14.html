The Vessel moves into Claude.

Overview

What we're building, and why

Eidola v1 was a portable runtime: an npm CLI, an MCP server, hook relays for Cursor and Claude Code, a local state socket and a browser Shrine. It worked, and then it went unused. The builder never opened it again after shipping it, and Claude, Cursor and others began adding similar features natively.

Claude Code now has a plugin API that delivers engine events, draws UI inside Claude and shapes the prompt. The PoC proved Eidola fits in it as one hooks module: a reacting Vessel in Claude's own pane, band and status line, and the awake Engram's Soul injected every turn. v2 rebuilds Eidola around that mod, keeps the creator side (Forge and Directory), and keeps the Shrine only where Claude can't draw.

Why

  • Daily use. A mod lives where the work happens (VS Code, the desktop app's Code tab, the terminal), so the Vessel is seen every day instead of in a tab nobody opens.
  • Less machinery. One plugin replaces the CLI, MCP server, relays, state socket, CLAUDE.md imports, compiled .mdc rules and the emotion classifier.
  • Creators stay central. Anyone can still make an Eidola, and the Directory still distributes them.

What success looks like

  • Installing is one marketplace add and one install. No npm, no settings edits, no restart beyond a new session.
  • On every local surface (desktop, VS Code, terminal) the Vessel reacts within one event of tool activity, and the Soul reaches the model every turn.
  • A creator can turn a GIF or MP4 into an Engram whose native tier animates in Claude and whose media tier plays on the Shrine.
  • A Kraken LCD or OBS source shows the live Vessel from a local session with no extra setup, and from a cloud session after one allowlist entry.

In scope

  • The mod: resolver, Soul injection, pane, band, status line, commands, placement
  • Engram spec v2 and a loader for packages on disk
  • Hosted relay on eidola.app and the Shrine as a viewer
  • Forge v2 (native SVG tier, GIF/MP4 converter, media tier) and Directory v2
  • Retiring the v1 runtime pieces

Out of scope

  • Monetization and the paid classifier tier (parked)
  • Cursor and any non-Claude host
  • Claude app chat outside Claude Code (mods may not run there)
  • Voice ($.audio.speak exists; later)
  • A browser extension or DOM scraping

In plain words

  1. You work in Claude Code. The engine raises events for each prompt, tool call, approval ask and turn end.
  2. The Eidola mod turns those events into one of nine Vessel states, and adds the awake Engram's Soul to each prompt (prompt.submit) and to the system prompt (prompt.compose). The Soul then travels with the request to the model.
  3. On local surfaces the mod draws the Vessel natively, in the pane, the band or the status line, wherever the person's placement says.
  4. The mod also posts each state change to a relay on eidola.app. The Shrine page subscribes and plays the Engram's media tier on a browser, an OBS source or the Kraken LCD.
  5. Engram packages come bundled with the mod or from the Directory, after creators make them in the Forge.
Options considered

Five decisions we weighed

Runtime

A · Native mod, Shrine fed by a hosted relay

Selected

The mod drives everything inside Claude. The Shrine becomes a viewer that subscribes to a relay on eidola.app.

Pros

  • One install path; no npm, MCP server or relays
  • One path for local and cloud sessions
  • Kraken and OBS keep working

Cons

  • A hosted service to run and secure
  • Cloud users add eidola.app to their allowed domains once
Runtime

B · Keep the v1 runtime

Rejected

CLI, MCP server, hook relays, local state socket and a local Shrine, as shipped.

Pros

  • Already built and working
  • Covers Cursor too

Cons

  • Heavy setup, and it went unused
  • Writes into CLAUDE.md and .cursor/
  • Nothing draws inside Claude

Rejected because v2 is Claude only and the mod covers the same ground with far less machinery.

Runtime

C · Native only, Soul only in cloud, no Shrine

Rejected

Drop the Shrine entirely. Cloud sessions get the Soul and nothing visual.

Pros

  • No hosted service
  • Smallest build

Cons

  • Loses the Kraken, OBS and second screens
  • Cloud sessions show nothing

Rejected once the cloud test showed hooks follow the environment's allowlist, so a relay can reach cloud sessions.

Shrine bridge

D · Localhost bridge only

Rejected

The mod posts state to a Shrine on 127.0.0.1:9743, as phase-viewer serves its dashboard.

Pros

  • No hosted service, no auth
  • Works for every local session

Cons

  • A cloud session's localhost is the cloud VM
  • Needs a local server running

Phase-viewer gets away with localhost because its data is files that travel by git. Vessel state lives for seconds and has no file trail. May return later as an offline fallback.

Engram distribution

E · One Claude plugin per Engram

Rejected

Each Engram ships as its own plugin through Claude's marketplace.

Pros

  • Claude's installer and updater for free

Cons

  • Two installed Engrams mean two Vessels and two Souls
  • The Directory loses its role

Rejected: one mod as the engine, Engrams as data it loads.

Technical decisions

Locked in

Claude only, delivered as a Claude Code plugin

Decision
Eidola ships as the eidola plugin from the AyeJK/eidola-mod marketplace: one hooks module, user scope.
Rationale
The plugin API gives events, UI and prompt shaping in one place, and the PoC proved each.
Constraints
No Cursor or other hosts. Install and update are claude plugin install and claude plugin update; the desktop app's own update check fails for this mod today.

The Soul rides two paths

Decision
Inject the Soul as hidden context on prompt.submit and as a system section on prompt.compose.
Rationale
prompt.compose alone didn't reach the model in cloud sessions; prompt.submit works everywhere.
Constraints
Under an organization-managed install only prompt.submit runs. Every Soul costs tokens every turn, so the spec caps its size.

One nine-state set

Decision
idle, thinking, working, waiting, responding, success, error, attention, sleeping, resolved from engine events.
Rationale
The engine reports state directly, so the tone classifier has no job.
Constraints
The emotion runtime and its tone states are retired, along with the runtime: state | emotion split.

Inside Claude, pictures are SVG and animation is CSS

Decision
The native tier is an SVG of at most 131,072 characters, animated by its own CSS. GIF and video play only on the Shrine.
Rationale
Desktop, VS Code and mobile draw only Svg. In VS Code, GIFs froze on frame 1 and WebM drew black, while CSS animation ran.
Constraints
The Forge converts uploads into the native tier and enforces the budget. Surface modules (Client) are no help: they draw text elements only.

The person chooses placement; the Engram suggests

Decision
placement option (default, both, pane, band, auto) and statusLine option, set in /config or with /eidola place. default follows vessel.placement, then both.
Rationale
Placement depends on the person's screen; the creator knows how the art reads at each size.
Constraints
An Engram can never stop the person opening the pane. Shrine targets join this list later.

The Shrine is a viewer behind a hosted relay

Decision
The mod posts state to a relay on eidola.app (a Vercel route over Supabase Realtime). The Shrine subscribes. No local server.
Rationale
Local hooks reach eidola.app directly. Cloud hooks reach whatever the environment allows, and a Custom network level takes an Allowed domains list.
Constraints
Cloud users add eidola.app once per environment. The relay needs per-person auth; network secrets (Pro and Max) can carry it in cloud without the session seeing it.

Engrams are data; one mod is the engine

Decision
The mod loads Engram packages (spec v2) from bundled copies and from the Directory. Engrams are never plugins themselves.
Rationale
Two plugins would mean two Vessels and the Soul injected twice.
Constraints
The loader needs a home for downloaded Engrams that also works in cloud sessions, where nothing local persists.

What retires

Decision
Retire cursor-hooks, cursor-ext, the claude-hooks relays, MCP awaken / sleep / launch_shrine, the .mdc compile, the CLAUDE.md import, emotion-runtime and the Phase 9 browser-extension plan. tool-state folds into the mod's resolver. The Shrine package shrinks to a viewer.
Rationale
The mod covers each of these with less to install and maintain.
Constraints
Existing installs keep their relay hooks in ~/.claude/settings.json until removed; v2 docs need an uninstall step.

Monetization is parked

Decision
No paid tier in v2.
Rationale
The old paid tier was the classifier, which no longer has a job.
Constraints
Nothing is built that assumes a paywall. Revisit after v2 has users.

Engram spec v2

A self-contained folder. What changes from v1: compiled artifacts and the runtime split are gone, voice_id is dropped, vessels/ moves inside the folder, and the native tier is required while media is optional.

# folder
{id}/
  engram.yaml
  SOUL.md
  vessel.yaml
  vessel/
    native.svg.json   # required: per-state SVG frames (pixels or converted)
    idle.webm         # optional media tier, Shrine only
    working.webm
# engram.yaml
spec: 2                  # format version, for migrations
id: wisp
name: Wisp
version: 1.0.0
author: ayejk
description: Quiet helper. Adds no voice.
tags: [minimal]
rights: original           # original | licensed: the creator's attestation
extensions: {}
# vessel.yaml
native: vessel/native.svg.json
media:                     # optional
  format: webm             # webm | mp4 | gif | lottie
  states:
    idle: vessel/idle.webm
    working: vessel/working.webm
fallback:                  # a missing state borrows another
  waiting: idle
  success: responding
  error: attention
placement: both            # suggestion only; the person's option wins
transitions: { default: crossfade, duration_ms: 300 }
playback: { idle_loops: true }
  • Draw order: media for the state, then media for its fallback, then native for the state, then native idle. Each surface draws the richest tier it can.
  • Validator: native idle is required; each native state stays under 131,072 characters; SOUL.md has a soft size cap, set after measuring token cost.

Does the cloud allowlist path work end to end?

Impact
Whether cloud sessions reach the Shrine. Also unknown whether an environment change reaches a running session or only new ones.
Owner
Jeremy: set Network access to Custom, add eidola.app, start a new cloud session, run /eidola.

How does the relay authenticate a person and pair a screen?

Impact
Relay design, the Shrine's pairing flow, and how the mod stores a token. Network secrets cover cloud on Pro and Max only.
Owner
Research: a secret userConfig field, $.session.authorize() for first-party hosts, or a pairing code.

Where do downloaded Engrams live, including in cloud?

Impact
The loader and the Directory install flow. Cloud VMs keep nothing local between sessions.
Owner
Research: $.store limits, fetching from eidola.app at session start, or bundling favourites.

Does the desktop app treat media the way VS Code does?

Impact
Only VS Code was tested. A difference would change what the native tier can carry per surface.
Owner
Test: /eidola media in a local desktop session.

Implementation handoff

For phase-planner

What exists: the mod at v0.3.0 in AyeJK/eidola-mod: resolver, Soul injection, pane, band, status line, placement, diagnostics and the media test, with 30 passing tests. The platform (AyeJK/eidola-platform, Next.js + Supabase on Vercel) still serves the v1 Forge and Directory.

First sprint: run case D and the cloud allowlist test, then replace the inlined Engrams with a spec v2 loader that reads bundled packages. Nothing else is safe to build until those two tests answer.

Key constraints: native pictures are SVG under 131,072 characters, animated by CSS; never let a hook break a tool call or a turn; every check runs before a push (claude plugin validate, tsc, claude plugin test); the person's placement always wins.

Phase 1

Mod core

Case D, cloud test, spec v2 loader, uninstall guide for v1 relays, version in /eidola.

Phase 2

Relay + Shrine

eidola.app relay on Supabase Realtime, auth and pairing, Shrine viewer with Kraken and OBS presets.

Phase 3

Forge v2

Pixel editor and GIF/MP4 converter with the SVG budget, media tier, spec v2 export.

Phase 4

Directory v2

Install into the mod, rights attestation and takedowns, v1 Engram migration.
