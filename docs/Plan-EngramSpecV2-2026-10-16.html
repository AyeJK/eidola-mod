Eidola · product plan

Engram Spec v2

Eidola is a live companion that reacts to what Claude is doing. This plan sets one folder format for every Engram it loads: the three bundled creatures (the Kraken, the Lich and the Wisp) first, then the ones people make themselves.

Draft 16 Oct 2026 Project: Eidola Author: Jeremy Kaye Source: AyeJK/eidola-mod 0.6.0 (75479c3)
Overview

What we're building, and why

Changed 16 Oct. Scenes only: v2 has no frames, so Spirit, Skull, Moon, Sigil and Starfield are removed with their pictures, and the bundle is the Kraken, the Lich and the Wisp (decisions 3, 4). Surfaces: one setting for all Engrams, three switches (Pane, Band, Shrine) and "hide the band while the pane is open", replaces placement (decision 5). Make your own: people create or remix Engrams with Claude, and each one ships as its own Engram plugin, made and published with an Eidola skill. That is Phase 2 now, replacing the settings-only folder (decision 14). No Soul: Eidola is the visual companion only and adds nothing to the prompt, so SOUL.md and Soul injection are gone (decision 9).

Eidola is a live companion that reacts to what Claude is doing: a creature in the pane, the band or the Shrine that moves with each prompt, tool and turn. Engram spec v2 is its package format. An Engram is a creature: a scene, a name, a description, colours and where it shows. Today the bundled Engrams are TypeScript objects in hooks/engrams.ts, and their pictures sit in vessels/<pack>/. v2 keeps the three that draw live scenes and turns each into a folder the mod reads at session start (engram.json and a vessel/ folder for picker thumbnails), writes the format down in the mod repo, and gives creators a checker. The v1 spec in eidola-runtime retires.

Why now

  • The spec on record describes a different product. eidola-runtime/docs/spec/engram-format.md is v1: Lottie, WebM, MP4 and GIF clips, a compiled Cursor rule, a CLAUDE.md import. None of it draws or runs in the mod.
  • Only code can add an Engram. Nobody can make one without editing the mod and opening a PR against TypeScript.
  • The format grew in code with no contract. shows, thumbnails, hud and scene arrived in 0.4–0.6 and the renderer and picker read them, but nothing defines them. The open bug where /eidola place both still shows a band-only Engram in the pane comes from that gap.
  • It has to be settled before anyone else builds on it. Creators build against the spec, so it gets locked before the mod goes public.

What success looks like

  • The Kraken, the Lich and the Wisp load from engrams/<id>/ folders. hooks/engrams.ts keeps the types and the loader and holds no Engram data. Their picker cards, thumbnails and scenes are unchanged, proven by snapshot tests taken before the move. The five frames Engrams are gone, on purpose, with their own test.
  • Eidola adds nothing to the prompt, on either path, proven by a test.
  • A person copies the template into their Engrams folder, picks a bundled scene, edits engram.json (name, description, HUD colours), runs /engrams, and it shows in the picker. No change to the mod.
  • A broken package never breaks a session. The loader skips it, and /eidola names the file, the problem and the fix.
  • docs/spec/engram-format.md lists only fields the mod reads, and each field has a test.
  • Where an Engram draws is decided by one function from one surfaces setting, and a band-only Engram never opens the pane by itself.

In scope

  • The v2 folder format and field reference
  • A loader for bundled Engrams and your own folder
  • One validator: loader, check script and /eidola check
  • Moving the Kraken, the Lich and the Wisp into folders
  • Removing the five frames Engrams and the frames path
  • Removing the Soul and all prompt injection
  • Spec docs in the mod repo: format and Vessel states
  • A template Engram to copy
  • The surfaces setting and the shows rule
  • A pointer from the v1 spec to v2
  • A local Shrine for the Kraken LCD, served by the mod, drawing the live 3D Engrams (Phase 4)

Out of scope

  • The Directory or any marketplace
  • Forge v2 and the GIF / MP4 converter
  • A media tier and the eidola.app relay
  • Cloud sessions: Eidola runs in local sessions only
  • Frames: per-state SVG pictures
  • Scene plugins: the later creator path, after Phase 4
  • Voice
  • Souls, personas or any prompt text (an optional link to a persona the person already has may come later, outside the format)
  • Surfaces beyond Claude Code for now

Data flow

From a folder to the pane

PersonMod componentOutside the modFiles and stored dataLater, not in v2

In plain words

  1. At session start, and again on /engrams, the loader reads each folder under the mod's engrams/ and under your Engrams folder. It reads only engram.json at this point.
  2. Each package is checked against the spec. A good one goes into the registry with its defaults filled in. A broken one goes on the skipped list with the file, the problem and the fix, and /eidola shows that list. Nothing throws.
  3. The picker lists the registry. Awakening an Engram stores its id in $.store, as today.
  4. whereItDraws picks where the awake Engram draws, from the surfaces setting and the Engram's shows. Nothing goes to the model: Eidola adds no text to any prompt.
  5. The resolver turns engine events into a state and a mood. The renderer draws the awake Engram's scene in that mood, with its HUD, on each surface that is switched on and that the Engram's shows lists. An error plays as a one-off effect on top. Thumbnails are read on first use and cached.
  6. Creators run the same checks before they share, through check-engram or /eidola check <id>.
Options considered

Four ways to define an Engram

A · One manifest: engram.json, naming a scene

Selected

Folder named by id. One JSON manifest that names the scene it draws, and a vessel/ folder for picker thumbnails. Per-state SVG frames and an optional SOUL.md were part of this option until 16 Oct; both are gone (decisions 3, 9).

Pros

  • No YAML parser needed in a hooks module that imports nothing but the plugin API
  • One file to validate, with a JSON Schema for editors
  • A package is small: a manifest and at most two thumbnails, each fitting one $.fs.read and one Svg
  • Manifests load at start and thumbnails load lazily

Cons

  • Drops the v1 file names engram.yaml and vessel.yaml
  • JSON has no comments for creators
  • Departs from the Oct 14 draft

Selected. v1 Engrams can't load in the mod whatever we name the files, because their clips are Lottie, WebM, MP4 or GIF and none of those draw in Claude. Keeping v1 names would buy nothing.

B · The Oct 14 draft: two YAML files, native.svg.json, optional media tier

Rejected

engram.yaml + vessel.yaml, all states packed into vessel/native.svg.json, and WebM / MP4 / GIF for the Shrine.

Pros

  • Already written up and reviewed once
  • Keeps v1 file names
  • Media tier is ready if the Shrine returns

Cons

  • Needs a YAML parser. Whether the hooks module can bundle npm packages is unverified.
  • Nine SVGs packed as strings in one JSON file are hard to view and edit (and v2 has no frames now)
  • Specifies a media tier for a surface v1 of the mod won't ship
  • Predates shows, thumbnails, hud and scene

Rejected. Its good parts carry over: spec as a version field, a rights attestation, extensions, and dropping voice_id. Its fallback map carried over too, until frames went on 16 Oct.

C · Keep Engrams in code, write the spec as docs only

Rejected

Document the TypeScript shape and leave hooks/engrams.ts as it is.

Pros

  • No loader, nothing to move
  • Fastest to finish

Cons

  • Only you can make Engrams
  • Docs and code drift apart again, as they have
  • No way to check a package

Rejected. A spec nobody can build against isn't a spec.

D · Each Engram as its own Claude plugin

Rejected

Ship every Engram through Claude's plugin marketplace.

Pros

  • Claude's installer and updater for free

Cons

  • Two installed Engrams mean two Vessels fighting over one pane
  • Engrams would have to ship code

Rejected on Oct 14, and still true: one mod is the engine, Engrams are data. A scene plugin is a different thing: it adds a scene, which is code, and Engrams name it (Next: scene plugins).

Wireframes

Technical decisions

Decided 16 Oct

Each of these stands unless you change it in review. Two depend on open questions and say so.

1 · A package is a folder named by its id Decided 16 Oct

Decision
<id>/engram.json (required) and <id>/vessel/ (optional, picker thumbnails only). No SOUL.md (decision 9). The folder name equals id.
Rationale
One manifest to parse and validate without a dependency. With no frames (decision 3), a package is just who it is and which scene it draws.
Constraints
v1 packages don't load. The bake script stops reading engrams.ts as text and reads manifests.

2 · The spec holds only what the mod reads Decided 16 Oct

Decision
Drop engram_version, voice_id, meta.created, meta.tags, vessel.type, vessel.pack and vessel.forge. Keep extensions as a free namespace the mod preserves and never reads. Unknown top-level keys warn rather than fail.
Rationale
Fields nothing reads go stale and mislead creators. That is how the v1 spec drifted.
Constraints
A field comes back only together with the code that reads it and a test. Tags return with the Directory, if it ever comes.

3 · One way to draw: scenes Decided 16 Oct

Decision
Every Engram names a scene in vessel.scene, which is required. For now that's a scene built into the mod: kraken, lich or wisp. Later it can also be a scene a scene plugin provides (Next). There are no frames: no vessel/<state>.svg files. The five frames Engrams, Spirit, Skull, Moon, Sigil and Starfield, are removed along with their vessels/<pack>/ folders, and the bundle is the Kraken, the Lich and the Wisp.
Rationale
One way to draw means one thing to spec, check, test and port to the Shrine. A package still reuses a scene with its own name, description and HUD colours, which is the preset-then-customize model.
Constraints
No Engram package ships code. A new bundled scene ships in a mod release. Each scene has a pane view, a band view and a Shrine canvas view, all driven by one simulation. The terminal still draws the text faces. Removing the five is a visible change, so it gets its own sprint and test (Phase 1, Sprint 1.3); a stored awake id for one of them is cleared at start with a one-line notice.

4 · Three moods, and error as an effect Decided 16 Oct

Decision
Scenes follow three moods, idle, working and attention, and blend between them. Error isn't a mood: it's a one-off effect on top of the current mood (the Kraken inks, the Lich is scorched), then the scene carries on. The resolver still has its nine states, and the HUD and status line may name them in text, such as "Lich · thinking".
Rationale
It's what the live scenes already do in 0.6.0. Nine pictures per Engram was the cost of the frames path, and that path is gone.
Constraints
No fallback table: every scene draws every mood. With nothing awake, the pane and band draw the resting Wisp's scene, dimmed, where the Wisp's sleeping frame drew before.

5 · Where an Engram draws: one surfaces setting Decided 16 Oct

Decision
One setting for all Engrams: three on/off switches, Pane, Band and Shrine, plus hide the band while the pane is open. They replace the placement option and its default / both / pane / band / auto values, and Engrams no longer carry a placement suggestion. Each Engram draws only on surfaces that are switched on and that its shows lists (pane, band, shrine). A band-only Engram never opens the pane by itself; you can still open the pane with /eidola, and it draws its band view there. A Shrine-only Engram draws only a one-line band with its name and the Shrine's URL, which the shrineBand option turns off (Q10). The status line stays its own toggle.
Rationale
You set it once, for every Engram, instead of a global option mixed with each Engram's suggestion. Fixes the bug where /eidola place both opened a band-only Engram in the pane, and keeps the Oct 14 rule that an Engram can never stop you opening the pane.
Constraints
One function, whereItDraws(surfaces, engram, isPaneOpen), replaces the reads spread across register.tsx (Phase 1, Sprint 1.5). Defaults: Pane on, Band on, hide the band while the pane is open on (as today's auto), Shrine off. /eidola place shows the switches and sets one, e.g. /eidola place band off. The Shrine switch arrives with the Shrine (Phase 4, Sprint 4.2); with it off, the mod starts no server and posts nothing.

6 · Two sources; bundled ids are reserved Decided 16 Oct

Decision
Bundled: ${$.plugin.root}/engrams/. Everything else: Engram plugins that announce themselves to Eidola at session start (decision 14), wherever they're installed from: your own in ~/.claude/eidola/engrams/ through the local eidola-local marketplace, or someone else's from their repo. An Engram plugin whose id matches a bundled one is marked not loading with a rename hint. Cloud sessions load bundled Engrams only.
Rationale
Silent overrides make bug reports impossible to read. To change a bundled Engram, remix it under a new id. A cloud VM's home isn't yours.
Constraints
Reads outside the mod's folder verified on Windows (Q2); home comes from USERPROFILE there, since HOME is unset. Changed 16 Oct: the second source was a folder of settings-only packages; decision 14 replaced it with Engram plugins.

7 · Manifests at start, thumbnails on first use Decided 16 Oct

Decision
Read every engram.json at session start and on /engrams. Read each thumbnail the first time the picker shows it, and cache it.
Rationale
Start-up stays small however many Engrams a person keeps.
Constraints
The checker reads every file. The loader checks a thumbnail's size when it first reads it, and uses the scene's bundled thumbnail if it's too big.

8 · One validator, three callers Decided 16 Oct

Decision
A pure hooks/validate.ts module, used by the loader (skip and report), by scripts/check-engram.mjs (run through the engine's test runner, as bake-thumbs.mjs does), and by /eidola check <id>. Plus docs/spec/engram.schema.json for editor hints.
Rationale
The checker and the loader can never disagree.
Constraints
The schema is generated from, or tested against, validate.ts. One source of truth.

9 · No Soul: Eidola is the visual companion only Decided 16 Oct

Decision
Eidola drops the Soul completely. An Engram is a creature: a scene, a name, a description, colours and shows. Packages carry no prompt text at all: no SOUL.md, no Soul fields, no Soul budget. Eidola injects nothing into the prompt on either path: the prompt.submit <eidola-soul> block and the prompt.compose eidola:soul section both go, along with the "quiet Soul". The Wisp loses its custom voice.
Rationale
Seven of the eight bundled Engrams only ever used the generated quiet Soul, which says little beyond "a companion is here". Personas already have homes in Claude Code: CLAUDE.md, output styles and skills. Injecting nothing costs zero tokens a turn and can't clash with a persona the person already has.
Constraints
Removed in Phase 1, Sprint 1.3, with a test that nothing is injected. Q4 (the Soul budget) goes away. A leftover SOUL.md in a package is ignored with a warning. Room is left for an optional link to a persona the person already has, later and outside the Engram format; nothing in v2 builds it.

10 · Rights attestation is required Decided 16 Oct

Decision
rights: "original" or "licensed", required.
Rationale
Costs nothing now. It's the first thing a PR intake or a Directory needs, and the v1 DMCA work showed what happens without it.
Constraints
It's the creator's word, not a check. Review still applies.

11 · No media tier Decided 16 Oct

Decision
v2 has no media field. GIF, MP4, WebM and Lottie aren't part of the format. The local Shrine draws the same native Vessel the pane does (decision 13). A creator who wants to keep clips puts them under extensions.
Rationale
They don't draw in Claude (VS Code froze GIFs on frame 1 and drew WebM black, Oct 14). The Shrine draws from the same Engram files and the same scene code, so one format covers every screen.
Constraints
Reverses the Oct 14 plan's media tier. Nothing a creator makes plays only on the Kraken.

12 · The spec lives in the mod repo Decided 16 Oct

Decision
docs/spec/engram-format.md, docs/spec/vessel-states.md (ported from v1's vessel-reactivity.md: the nine resolver states, the three moods scenes draw, and the error effect), and docs/spec/engram.schema.json. The v1 spec files get a one-line pointer to the mod.
Rationale
It cuts the last link to eidola-runtime, so that repo can be archived.
Constraints
The comment in hooks/resolver.ts moves to the new doc.

13 · The mod serves its own local Shrine Decided 16 Oct

Decision
A small server that ships with the mod, shrine/server.mjs (Node, no dependencies), is started by the mod with $.process.spawn and runs on 127.0.0.1:9743 for the session's life. The mod posts the state, mood and ink count. The page at /shrine/ draws the Engram itself, from its files and from the same simulation code the pane runs. No relay, no eidola.app.
Rationale
We run local sessions only, so the cloud reach a relay gave is worth nothing. A hosted relay means auth, pairing and a service to run, all for that. The Oct 14 plan rejected a localhost bridge only because of cloud sessions.
Constraints
Local sessions only. Port 9743 stays, so an existing CAM setup keeps working, and the v1 Shrine must be uninstalled first. Spawning and serving verified on Windows and Linux (Q7, Q8).

14 · Engrams you make are plugins, made with Claude Decided 16 Oct

Decision
People make Engrams the way the Kraken and the Lich were made: by describing them to Claude, from nothing or by remixing any Engram. Each one ships as its own small Claude Code plugin, an Engram plugin, with its engram.json and its own drawing code. Eidola hands it the drawing of the creature and keeps the frame, HUD, picker and Shrine. An Eidola skill, shipped with the mod, creates, remixes, checks and publishes them. Publishing means a GitHub repo others install with two commands.
Rationale
A folder of settings naming a bundled scene couldn't change the creature itself, which is the point. A mod can't load code from a folder (Client modules must sit inside the plugin; no import() or eval), so a plugin is the only way to ship code. The 16 Oct probe showed another plugin can read Eidola's state, call its commands, draw in the band and serve a Shrine module.
Constraints
Eidola's pane must hand off with next(e), which the probe hasn't proven yet: Phase 2 tests it first. Eidola's PluginState becomes a public, versioned contract. A broken Engram plugin falls back and is marked not loading; it never breaks the session. Replaces the settings-only "Your Engrams" folder of the earlier Phase 2 and the "scene plugins later" direction.

Phase 4

Local Shrine for the Kraken LCD

The Vessel off-screen again: on the Kraken's pump display, a browser tab or an OBS source. The Shrine page draws the Engram itself, from the same files and the same simulation code the pane runs, so it isn't held to the pane's limits. The mod only tells it what's happening.

How it works

  1. The Shrine runs only while its switch in the surfaces setting is on (decision 5); it's off by default. With it on, on session.start the mod asks http://127.0.0.1:9743/health. If nothing answers, it starts node <mod>/shrine/server.mjs with $.process.spawn, passing it the bundled and personal Engram folders. The server lives as long as the session.
  2. On each state, mood or ink change, debounced, the mod posts { engram, state, mood, ink } to /state with $.http.fetch. A few bytes, fire and forget.
  3. The server serves the page, its bundled script, and the awake Engram's files (engram.json, thumbnails) straight from the folders. It pushes each change to every open page over server-sent events.
  4. The page draws the Engram itself. Every Engram is a scene, so the page runs that scene's simulation on a canvas, and the Kraken, the Lich and the Wisp move live in 3D at the screen's own frame rate, blending between moods. A rise in the ink count plays the error effect. There's no frames path.
  5. The page fits whatever window it's in (see Any size). On CAM's Kraken browser (window.nzxt.v1 or ?kraken=1) it takes the screen's size, shape and targetFps and draws a 640 × 640 circle. That's ported from the v1 kraken-detect.ts and kraken-setup.ts.
  6. With several sessions open, the last one to post shows. When the session that started the server ends, the server goes with it. The next post from another session finds nothing and starts its own.
  7. /eidola shrine prints the URL and CAM's deep link: nzxt-cam://action/load-web-integration?url=http://127.0.0.1:9743/shrine/, with the cam-redirect.nzxt.com fallback.

shrine/kraken.canvas.tsTicks the simulation at the screen's frame rate and paints it on a canvas, on a finer pixel gridShrine page

The Lich (lich3d.ts, glyphs instead of pixels) and the Wisp split the same way. shrine/page.ts imports the simulations and is bundled to shrine/page.js with esbuild. The bundle is committed, because installing a plugin runs no build. The pane and the LCD run separate copies, so they answer to the same moods but don't move in lockstep.

Any size

The Shrine can be the pump's round screen, a browser tab, an OBS source, or a strip as thin as the band. There's no resolution setting: the page fits the window it's in. A setting couldn't work anyway, because one server feeds several screens at once and each needs its own size.

  • The window is the frame. The canvas matches the window (times the device pixel ratio) and redraws on resize. The simulation gets the canvas size as its frame, as the pane's Kraken already gets its cols and rows today: camera, sizeOf, pickSpot and isOutOfView all work from the frame's width and height. So the creatures roam the whole window and leave and re-enter at its real edges, at any size.
  • The shape picks the view. Round on the Kraken, wide at about 2.5:1 or wider, regular in between. The view sets the camera and the creature's size.
  • In-between shapes get a blended size. Today sizeOf has two rules, the band's and the pane's. The Shrine blends smoothly between them, so a 16:9 tab or a 3:1 strip gets a fitting creature. The pane keeps its two sizes exactly.
  • Grid density follows the size. A minimum cell size keeps the pixel look; a bigger window gets more cells, up to the frame budget, and coarsens when a frame runs long.
  • Overrides go in the URL, per screen: ?view=round|wide|regular, ?bg=transparent for OBS, ?hud=0 to drop the state and camera labels. ?kraken=1 already works this way.

No safe area in the spec: the creatures move in and out of frame by design, so nothing pins them inside it.

Shrine-only Engrams

The Shrine isn't held to the pane's limits: 131,072 characters a picture, 700 Boxes a frame, 10 ticks a second. So some Engrams can be made for it alone, such as a denser Kraken or a Lich in full particle fire. They set "shows": ["shrine"].

  • They're scenes, so for now they're first-party: a new one ships in a mod release. Later, a scene plugin could provide one (Next).
  • Awake, the status line still shows their name and state. The band shows one line, their name and the Shrine's URL, unless you turn it off with the shrineBand option (Q10).
  • The picker gets a Shrine filter, and their cards say "Shrine only".

Phase 2 · see decision 14

Next: scene plugins

Brought forward on 16 Oct: this is now Phase 2, as Engram plugins made with an Eidola skill (decision 14). The notes below are the background it started from; where they say an Engram is data that names another plugin's scene, decision 14 supersedes them: an Engram you make carries its own scene.

  • Engrams stay data. An Engram package has no code and no prompt text. It names a scene, either one bundled in Eidola or one a scene plugin provides.
  • A scene plugin is code. It draws the scene in the pane and band, and gives the Shrine a browser module to run on its canvas. It ships no Soul and adds nothing to the prompt either (decision 9).
  • Eidola stays the engine. It still owns the HUD, the frame and corner, the resolver and where things draw.

What the 16 Oct probe found

A throwaway second plugin, eidola-mod/.probe/eidola-scene-probe, notes in eidola-mod/.probe/SCENE-PROBE.md.

QuestionResult
Can it read Eidola's state?Yes. $.state.get reads Eidola's PluginState with literal { plugin: 'eidola', key } refs.
Can it run Eidola's commands?Yes, with $.command.run. Each run shows in the transcript.
Can it tell Eidola has loaded?Yes. Its plugin.register hook saw Eidola load, with Eidola's root path. This depends on load order.
Can the Shrine load its browser module?Yes. A Shrine-style page served by Node imported the plugin's shrine-scene.js from the plugin's folder. A path escaping that folder got a 403.
Can it draw in the band?Yes, in a desktop session. Its AbovePrompt ui.render hook ran because Eidola passed next while the band was hidden.
Can it draw in the pane?No. Eidola's Pane ui.render hook (register.tsx, around line 1004) never calls next, and the probe's hook sits inside Eidola's.

So Eidola needs a hand-off: when the awake Engram's scene comes from a plugin, Eidola's Pane hook calls next(e) and places the returned tree under its own HUD, frame and corner. This is untested.

Open for that phase

  1. The hand-off. Does next(e) from Eidola's Pane hook return the plugin's tree, and can Eidola place it under its HUD, frame and corner? Same for the band.
  2. Discovery. Does Eidola find scene plugins by hooking plugin.register, or do scene plugins announce themselves? Load order matters for the first.
  3. A public contract. Eidola's PluginState (the awake Engram, the mood, the ink count) would become a public, versioned contract that scene plugins read.
  4. The Shrine. How the Shrine finds and loads a scene plugin's browser module, and which folders it may serve.
  5. The creator skill. A Claude skill that scaffolds a scene plugin: what it generates, and how a creator tests it.
